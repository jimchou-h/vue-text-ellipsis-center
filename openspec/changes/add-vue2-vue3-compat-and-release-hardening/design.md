## 背景

当前仓库混合了多个阶段的状态：一部分是迁移后的 Vue 3 TSX 实现，另一部分是历史 Vue SFC/声明产物，同时包结构处于部分重构状态。构建输出路径与包元数据未对齐，测试对内部实现存在耦合，导致发布可预测性不足。

产品方向已明确：在恢复稳定可发布流程的同时，正式支持 Vue 2 与 Vue 3。

约束条件：
- 尽量保持单一包名（`vue-text-ellipsis-center`）。
- 除非显式标注，不破坏现有对外使用契约。
- 发布结果必须可复现，并可在 CI 中自动校验。

## 目标 / 非目标

**目标：**
- 设计一套可在同一仓库内支持 Vue 2 与 Vue 3 的运行时兼容架构。
- 收敛包元数据、构建输出与类型声明，形成唯一且一致的发布契约。
- 建立基于用户可见行为的 Vue 2 + Vue 3 版本矩阵验证策略。
- 提供明确的 Vue 2 / Vue 3 示例与文档入口。

**非目标：**
- 不做与兼容性/发布稳定性无关的功能重写或交互改造。
- 不引入与本次目标无关的示例或文档重构。
- 不承诺支持声明矩阵之外的历史 Vue 版本。

## 关键决策

1) 运行时兼容模型：采用基于 `vue-demi` 的适配策略。
- 决策理由：在单包发布前提下，维护成本最低，且是双版本 Vue 组件库成熟且可复用的生态路径。
- 备选方案：
  - 按大版本拆分双包（`-v2`/`-v3`）：实现直接，但维护重复、用户心智分裂。
  - 单包多子路径构建（`/vue2`、`/vue3`）：灵活，但打包与类型维护复杂度明显上升。

2) 发布契约：统一由单一发布源产出标准化构建结果。
- 决策理由：可复现发布依赖唯一发布源，且 `main/module/exports/types/files` 必须与产物严格一致。
- 备选方案：
  - 保留根包与子包混合治理：高概率出现元数据漂移和误发布。

3) 测试策略：从白盒内部状态断言转向黑盒行为断言，并执行版本矩阵。
- 决策理由：内部实现形态可变，但用户可见行为才是兼容契约本体。
- 备选方案：
  - 继续操作组件内部状态进行测试：脆弱且已在现状中表现为不稳定。

4) 发布硬化门禁：发布前强制通过构建、矩阵测试与元数据一致性检查。
- 决策理由：在发布前拦截入口/类型损坏与跨版本回归，降低线上故障风险。

## 风险 / 权衡

- [Vue 2 在 Composition API / JSX 上的语义差异] -> 缓解：隔离框架差异辅助层，优先行为测试，采用双端可验证的最小语法子集。
- [依赖兼容漂移（`vue-demi`、VueUse 相关）] -> 缓解：锁定支持区间并在 CI 矩阵持续验证；必要时以本地实现替换不可移植能力。
- [打包收敛导致导入路径变化风险] -> 缓解：尽可能保持向后兼容导出；不可避免变更提供明确迁移说明。
- [迁移周期长、分支复杂度上升] -> 缓解：按纵向切片推进（发布基线 -> 运行时适配 -> 矩阵测试 -> 示例文档）。

## 迁移计划

1. 先稳定发布契约与产物路径（目标是不改变业务行为）。
2. 引入运行时适配抽象并接入组件/插件入口。
3. 建立并跑通 Vue 2 + Vue 3 测试矩阵。
4. 更新 Vue 2 与 Vue 3 示例和文档。
5. 增加发布检查清单/自动化门禁，并执行 `npm pack` 干跑验证。
6. CI 与人工 smoke 均通过后再发布。

回滚策略：
- 每个纵向切片独立提交；若某切片兼容失败，仅回退该切片，保留已验证通过的切片成果。

## 已确认决议

- Vue 2 支持范围同时覆盖 `2.6 + @vue/composition-api` 与 `2.7`，并与 Vue 3 一起纳入正式支持矩阵。
- 主实现不再以 TSX 作为唯一路径，改为更中性的渲染实现（`h`/render 函数优先），以降低跨版本编译与语义差异风险。
- 运行时路径优先使用本地工具能力（例如尺寸监听与可见性监听封装），减少对 VueUse 的核心依赖，以提升 Vue 2 侧可控性与稳定性。
